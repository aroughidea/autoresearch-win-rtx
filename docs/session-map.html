How one autoresearch session runs

Autoresearch hands model training to an AI coding agent: a chat assistant, like the ones you use, that can also edit files and run programs, here left to work alone, often overnight. The goal of the session is to improve the training recipe for a small language model: a GPT-style transformer of about 19 million parameters that learns to continue text. The session starts from a starter recipe (the file train.py), a dataset, a tokenizer, a run duration of 10 minutes, and a session length of 10 hours. Three initial 10-minute training runs of the starter recipe build the baseline: their average sets the baseline score, and their spread measures the noise, how far apart two runs of the same recipe land. While the 10-hour session has time left, the agent changes one thing in train.py, the training recipe, and trains again. Each run always trains for its full 10 minutes; scoring and the sample stories add a few minutes more, so in the session's last 20 minutes the agent starts no new run.

Why run a session

For the agent, the goal is the best recipe. For you, the point is to see that changing a design decision changes the final experience in a specific way, and the record keeps every decision, kept or undone. Some decisions show plainly: your choice of dataset changes the sample stories, and the vocabulary changes the model's size and how it writes early in training. Most of the agent's changes are too small to read in the stories, which is why the agent needs a score.

The record

Each session has its own folder, sessions/<name>/. It holds every version of train.py that trained, one entry for every run, and a pointer to the best version. train.py itself is only the working copy that the agent edits. A run's entry is written once the run has been scored: its version, its score and its sample stories. The agent's decision completes it: keep, discard, or crash for a run that never finished, with a few words on what was tried. The sample stories are what the model writes when given four fixed story openings, such as “Once upon a time”, at set moments during training and again when training ends.

The agent decides with one of two commands, keep or undo. Keep moves the pointer to the version that just ran and saves a copy of the model. Undo puts train.py back to the version the pointer marks. Because every change starts from the best version, that is also the version the undone change started from; going back to the previous run instead could mean going back to an idea that was already undone. Nothing is deleted from the folder: every version and every entry stays. To share a session, share its folder.

The scoreboard

Read together, the run entries are the scoreboard: one row per run, with its version of train.py, its score, the decision and what was tried. results.tsv in the session's folder is the same table as a file, rewritten after every decision.

The score

After training, each model is given text that was kept out of its training data. The score measures how surprised the model is by that text: how badly the model predicts each next piece. The professional name is validation bits per byte, val_bpb. Lower is better. The test is fixed: the agent cannot change it.

The score is counted per byte of text rather than per token, so models with different vocabularies can be compared. Scores compare only runs on the same dataset, and only runs of the same length.

Two runs of the same recipe rarely score exactly the same. The recipe and the model's starting weights are identical; what differs is mainly how many training steps the laptop fits into the 10 minutes. So each session begins by training the starter recipe three times. Their average is the first score to beat, and their spread is the session's noise: a difference smaller than that may be luck. The rule stays simple, though: a run that beats the best is kept. When a gain is smaller than the noise, the agent says so in its description, so you can weigh it when you read the results.

Three time scales

A training run: 10 minutes

Every run, the first included, trains a new model from scratch. The model's weights change after every batch of text, a step; nothing else in the session changes a model's weights. One full pass through the data is an epoch. A large dataset like TinyStories is not read even once in a run; a small one like Folktales is read many times over, and the model can start to memorise its training text.

A session: 10 hours

The first three runs train the starter recipe as it is, to set the baseline and measure the noise. After that the agent starts each run from the best version so far and changes one thing in train.py: for example the learning rate (how big each adjustment to the weights is), the model's size and shape, or the schedule (how the adjustments shrink toward the end of a run). The code that loads the data, builds the tokenizer and computes the score is fixed for the session, and so are the agent's instructions: the record refuses to train if any of them changes, or if a different dataset, tokenizer or run length is set. A kept model is saved on the laptop so you can try it later; an undone one is not kept. Either way the next run trains a new model from scratch. Only the recipe carries forward.

Between sessions: you

You read the results, share them, and choose what to run next: the dataset, the tokenizer, the session's length, each run's length. You can also edit the agent's instructions, program.md, but there is seldom a reason to: they set how experiments are run and judged, and the agent supplies the ideas. Nothing in a session changes the agent itself.

The model

A small GPT: a transformer of about 19 million parameters. Parameters here are the numbers the model learns in training, its weights, not settings such as temperature. train.py counts them at the start of every run, and the run's entry keeps the count.

Much of that size depends on the vocabulary, because the model keeps rows of numbers for every token in it. The same recipe makes a model of about 19 million parameters with the vocabulary built from the dataset (8,192 tokens), 46 million with Phi-3's (32,011) and 67 million with GPT-2's (50,257). The agent may also change the model's shape, so the count can change during a session.

Pretraining only

Language models are usually made in three steps: pretraining, where the model learns to predict the next token from a lot of text; fine-tuning, on examples of prompts and good responses; and learning from human feedback, where judgments of its responses change the model. Every run here is step 1 only, at laptop scale. So these models continue whatever you give them instead of answering it.

The score is not feedback. It never changes a model's weights; it only decides which recipe the agent keeps, and the next model is trained from scratch.

Is this recursive self-improvement?

Recursive self-improvement means an AI system that builds its own improved successor, which is then better at building the next one. This is not that. The loop changes train.py, the recipe for a small model that can only continue text. Nothing changes the agent, which ends the session as it began. The score measures how well the small model predicts text, not how well anyone does research. And people choose the data, the rules and what happens next. The full argument, and what would have to be in place for it to be recursive self-improvement, is in the project's notes on training decisions.
